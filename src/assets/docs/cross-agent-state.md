# How Do You Maintain State Across Agents?

## Interview Question

**“How do you maintain state across agents in your Agentic AI architecture?”**

---

# Strong Interview Answer

I maintain state using a **shared workflow state managed by the orchestration layer**, while keeping agent-specific memory and enterprise business data separate.

In my architecture, **LangGraph maintains the workflow state** as the request moves through the Coordinator, Delegators, and Workers.

The state contains only the information required for orchestration, such as:

* Request ID / correlation ID
* User intent
* Current workflow stage
* Selected Delegator
* Selected Workers
* Task status
* Intermediate results
* Errors/retries
* Relevant context
* Final response

Each agent reads the state, performs its responsibility, and writes its result back into the workflow state.

For independently deployed agents, I don't rely on in-memory state. I persist the required state/checkpoints in a durable store and pass only the necessary context between agents.

So the principle is:

> **Centralized workflow state, decentralized agent execution.**

---

# Functional Architecture

```text
                    User Request
                         ↓
                   Coordinator
                         ↓
                 ┌───────────────┐
                 │ Workflow State│
                 └───────┬───────┘
                         ↓
                   Delegator
                         ↓
              ┌──────────┼──────────┐
              ↓          ↓          ↓
           Worker A   Worker B   Worker C
              ↓          ↓          ↓
              └──────────┼──────────┘
                         ↓
                  Updated State
                         ↓
                    Coordinator
                         ↓
                       User
```

The important point is that agents don't have to independently maintain the entire conversation or workflow.

They operate on the **relevant portion of shared state**.

# Example

Suppose the user asks:

> **“Analyze this semiconductor defect image and identify the root cause.”**

The initial state could look conceptually like:

```json
{
  "request_id": "REQ-12345",
  "intent": "defect_analysis",
  "domain": "manufacturing",
  "input_type": "image",
  "status": "started"
}
```

The Coordinator identifies the Manufacturing Delegator.

The state becomes:

```json
{
  "request_id": "REQ-12345",
  "intent": "defect_analysis",
  "domain": "manufacturing",
  "delegator": "manufacturing",
  "status": "delegated"
}
```

The Delegator decomposes the task:

```json
{
  "required_capabilities": [
    "image_analysis",
    "historical_search",
    "root_cause_analysis"
  ]
}
```

Workers then contribute results.

```json
{
  "vision_result": "...",
  "rag_result": "...",
  "rca_result": "...",
  "status": "completed"
}
```

The final state contains enough information for the workflow to produce the response.

# What Exactly Do You Store in State?

I typically divide state into several categories.

## 1. Workflow State

This controls execution.

```text
current_node
current_agent
workflow_status
task_status
retry_count
next_action
```

Example:

```json
{
  "current_agent": "vision-worker",
  "status": "running",
  "retry_count": 1
}
```

---

## 2. Task Context

Information required to complete the current task.

```text
user_intent
domain
task_description
required_capabilities
relevant_entities
```

---

## 3. Intermediate Results

Outputs generated by Workers.

```text
vision findings
retrieved documents
analytics results
RCA findings
confidence scores
```

---

## 4. Control Metadata

Useful for enterprise operations.

```text
request_id
correlation_id
trace_id
timestamp
agent_version
workflow_version
model_version
```

This helps with distributed tracing and debugging.

# State vs Memory vs Business Data

This distinction is extremely important in an architect interview.

I don't treat everything as "agent memory."

### Workflow State

Answers:

> **“Where am I in this execution?”**

Example:

```text
Coordinator → Manufacturing Delegator → Vision Worker
```

---

### Conversation Memory

Answers:

> **“What has the user discussed previously?”**

Example:

```text
Previous user preferences
Previous conversation context
Previous interactions
```

---

### Agent Memory

Answers:

> **“What information should this agent retain for future reasoning?”**

Depending on the use case, this could be short-term or long-term memory.

---

### Business Data

Answers:

> **“What is the authoritative enterprise information?”**

Examples:

```text
Manufacturing database
Quality system
ERP
CRM
Knowledge base
Data warehouse
```

Business data should generally remain in the appropriate enterprise system rather than being copied into agent state.

              └───────────┬───────────┘
                          │

# How Does LangGraph Help?

LangGraph provides a stateful execution model where nodes operate on a shared graph state.

Conceptually:

```text
State
  ↓
Coordinator Node
  ↓
Updated State
  ↓
Delegator Node
  ↓
Updated State
  ↓
Worker Node
  ↓
Updated State
```

The state can be checkpointed so that the workflow can recover from interruptions or failures.

For example:

```text
Coordinator
     ↓
Delegator
     ↓
Vision Worker
     ↓
Checkpoint
     X
Failure
     ↓
Resume
     ↓
RCA Worker
```

This is one reason a stateful orchestration framework is valuable for long-running agent workflows.

# What Happens When Agents Are Independently Deployed?

This is where state management becomes more important.

Suppose:

```text
Coordinator
     ↓ A2A
Delegator
     ↓ A2A
Vision Agent
```

I would **not assume that these agents share process memory**.

Instead, I use explicit context propagation.

Conceptually:

```json
{
  "request_id": "REQ-12345",
  "task_id": "TASK-789",
  "parent_task_id": "TASK-456",
  "context": {
    "intent": "defect_analysis",
    "domain": "manufacturing"
  },
  "required_output": "defect_findings"
}
```

The Worker receives the minimum context required to perform its task.

It returns:

```json
{
  "task_id": "TASK-789",
  "status": "completed",
  "result": {
    "defect_type": "..."
  }
}
```

The Delegator then merges that result into the workflow state.

---

# Why Not Pass the Entire State to Every Agent?

I avoid that.

Passing the entire state creates several problems:

* Large token consumption
* Higher latency
* Higher LLM cost
* Unnecessary data exposure
* Security/privacy concerns
* Context-window pressure
* Tight coupling between agents

Instead, I use **scoped context propagation**.

```text
Global Workflow State
        ↓
Context Selection
        ↓
Relevant Context
        ↓
Worker
```

For example, the Vision Worker may only need:

```text
image
defect ID
analysis instructions
```

It doesn't need:

```text
user's entire conversation
finance information
other domain data
internal workflow history
```

---

# How Do You Maintain Consistency?

I use a combination of:

### Correlation IDs

Every request receives a unique identifier.

```text
request_id = REQ-12345
```

All agent tasks inherit the correlation ID.

```text
Coordinator
   REQ-12345
      ↓
Delegator
   REQ-12345
      ↓
Vision Worker
   REQ-12345
```

This allows us to trace the entire workflow.

---

### Task IDs

Individual tasks receive their own IDs.

```text
Request
  REQ-12345

Tasks:
  TASK-001 → Vision
  TASK-002 → RAG
  TASK-003 → RCA
```

---

### Versioned State

For long-running workflows, I also track:

```text
workflow_version
agent_version
model_version
state_schema_version
```

This is useful when agents evolve independently.

---

# What Happens If an Agent Fails?

Because the workflow state is persisted, the system doesn't necessarily need to restart from the beginning.

Example:

```text
Coordinator
     ↓
Delegator
     ↓
Vision Worker
     ↓
Checkpoint
     ↓
Vision Worker fails
     ↓
Retry / Fallback
     ↓
Resume Workflow
```

The system can use policies such as:

```text
Retry
Fallback Worker
Skip Optional Task
Human Intervention
Fail Workflow
```

The appropriate behavior depends on whether the failed task is critical.

# Parallel Workers and State

Suppose the Delegator launches three independent Workers:

```text
                 Delegator
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
       Vision      RAG     Analytics
          │         │         │
          └─────────┼─────────┘
                    ↓
             Result Aggregator
                    ↓
              Updated State
```

Each Worker produces its own result.

The orchestration layer then merges those results into the state.

Conceptually:

```text
state.vision_result
state.rag_result
state.analytics_result
```

Then the RCA Worker can consume the combined evidence.

This is an important reason to explicitly define a **state schema**.

---

# State Schema Design

I would define a controlled state model rather than allowing every agent to write arbitrary information.

For example:

```python
class WorkflowState:
    request_id: str
    intent: str
    domain: str
    delegator: str
    current_task: str

    task_status: dict

    worker_results: dict

    errors: list
    retry_count: dict

    final_response: str
```

This provides a contract between orchestration components.

---

# State Ownership

Another important design principle is:

> **Not every agent should be allowed to modify every piece of state.**

For example:

```text
Coordinator
    owns → routing information

Delegator
    owns → domain task decomposition

Worker
    owns → worker result
```

Conceptually:

```text
Coordinator
   ↓
routing fields

Delegator
   ↓
task/decomposition fields

Worker
   ↓
execution/result fields
```

This reduces accidental state corruption and improves governance.

# Architect-Level Answer

> “I separate workflow state from memory and business data. LangGraph manages the workflow state for the Coordinator → Delegator → Worker execution, and I persist checkpoints for recovery and long-running workflows. Agents don't share process memory; instead, they receive the minimum context required for their task and return structured results that are merged back into the workflow state. I use request IDs, task IDs, and versioned schemas for traceability and consistency. Long-term memory is maintained separately, and enterprise systems remain the source of truth for business data. This gives us centralized workflow coordination while keeping individual agents independently deployable and loosely coupled.”

# Common Interview Trap

### Interviewer:

**“So all your agents share the same state?”**

Don't simply say **yes**.

A better answer is:

> “They participate in the same workflow state, but I don't expose the entire state to every agent. The orchestration layer maintains the canonical workflow state, and each agent receives a scoped view containing only the context required for its task.”

That's a much stronger enterprise answer.

---

# Golden Architecture Principle

```text
Workflow State
      ↓
Canonical execution context

Agent Memory
      ↓
Long-term / reusable knowledge

Enterprise Data
      ↓
Source of truth

Agent Context
      ↓
Minimum required information
```

### Memory Trick

**STATE = SCOPE + PERSIST + TRACE**

* **SCOPE** → Send only required context
* **PERSIST** → Checkpoint durable workflow state
* **TRACE** → Request ID + Task ID + correlation

> **“Centralized workflow state, scoped context, independent agent execution.”**
